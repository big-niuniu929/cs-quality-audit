# 版本线

两段提交对应两个可运行状态。

| tag | 时间 | 形态 | 关键差别 |
|---|---|---|---|
| `v4.0-legacy` | 2026-10 | 单文件 PyQt 应用，`app.py` 约 80 KB | 导入会话 → 总览 → 双击看聊天 → 人工复核 → 导出。评分与角色识别写在代码里，改口径要改代码 |
| `v5.2.0` | 2026-11 | 拆包 `src/qc_engine/` + 引擎化 | 规则/评分/解析/存储全部抽出成模块，口径改成 YAML 配置；加 AI 质检维度与「爆单一铲」副驾；双看板；macOS 打包 |

## 为什么拆包

v4 的痛点很具体：评分口径一改就要动 `app.py`，而 `app.py` 同时管界面和规则，改一行要重新打包验证整条链路。v5 把「界面」和「判定」分开：

- `rules/engine.py` + `config/rules.yaml`：商机分级的关键词唯一来源，改 YAML 即可改规则
- `quality/scoring.py` + `config/scoring.yaml`：6 维四档制，档位标准可配置
- `parser/`：会话 `.log` 与 `.xlsx` 两种来源分别解析，再归一成同一模型
- `storage/database.py`：SQLite 负责批次、会话、消息、评分、复核留痕
- `services/pipeline.py` / `runner.py`：把「导入 → 规则 → 评分 → AI」串成可中断、可续跑的流水线

## 评分标准怎么演进的

1. 最初：人工抽查，看到问题就口头说，没有统一标准
2. 第一版规则：六个维度各自 20 分，靠关键词命中给分 —— 结果「话术匹配度」虚高，因为套话也能命中关键词
3. v5.0：改成三层档位（每维扣 33%/63%/100%），话术匹配、问题解决交给 AI 质检，未跑时显示「待AI质检」
4. v5.2：换成 **100 分四档制**（优秀/良好/合格/不合格，及格 60），并把四档的达标条件做成应用内可查看的「评分规则」——让客服知道分数是怎么来的

这条线的原则是：**分数必须能追溯到具体某一句话**，否则复核没有意义。
